FGC Widget – Deploy package
===========================
Date: 2026-08-03
Supersedes: 2026-07-25 and 2026-07-28 packages

Addresses the report of 2 August: an incident sent from the app at ~23:30
produced no sound and was only noticed after refreshing the CMS.


WHAT CHANGED
------------
A. Server – silent incidents (root cause of the report)

   Under the pending-count rule confirmed on 2026-07-28, an alert leaves the
   widget's pending set as soon as an operator handles it (updatedAt). The
   server decided everything from the pending count and sent nothing when that
   number was unchanged.

   So when an operator handled an alert in the same 2-second poll window in
   which a new incident arrived, the removal and the arrival cancelled out and
   the server sent no message at all: no sound, no blinking, no count update.
   The widget kept showing a number that was arithmetically correct, which is
   why nothing looked wrong until someone opened the CMS.

   The poll now also reads MAX(id) over the pending set and keeps a monotonic
   watermark of the highest incident id seen. A broadcast is emitted when the
   count changes OR the watermark advances, and the sound is driven by the
   watermark instead of the count direction.

   The pending-count rule itself is UNCHANGED from 2026-07-28:
     state = 1 AND updatedAt IS NULL AND fromCms IS NULL AND user != 'prova'
   The widget number is intentionally NOT the CMS "Alertes pendents" total and
   may legitimately be lower.

B. Widget – alert sound was disarmed by every restart

   The sound-duration selector (Off / 1' / 3') defaulted to Off and was never
   persisted, so every relaunch of the widget silently reset it to Off and no
   incident could produce sound until an operator selected a duration by hand.

   The setting is now stored on the workstation and restored at startup. A
   first-ever install now defaults to 1 minute rather than Off. An operator who
   deliberately selects Off keeps Off across restarts.

   NOTE: this is hardening, not the cause of the 2 August report. Please
   confirm you are happy with the audible first-run default before rollout.

DEPLOY ORDER
------------
A. Server (fixes the reported incident)

   1. On the Symfony host, replace:
        src/WebSocketServer.php
      with the file from fgc-websocket-patch/src/.

   2. Restart the WebSocket process:
        app:websocket-server

   3. Confirm the process is listening on port 8080.

   Optional pre-check, from the Widget repository:
        php -l server-patch/src/WebSocketServer.php
        php tests/server-websocket-smoke.php

B. Widget (sound persistence)

   Rebuild and distribute from the widget source:
        npm ci
        quasar build -m electron
   Then sign and notarize with your production Apple credentials.

   The server fix works with the currently installed widget, so the rebuild can
   follow separately if that is easier to schedule.


ACCEPTANCE TEST
---------------
1. Open the widget. Confirm it is online (not stuck on DESCONECTAT).

2. From the FGC mobile app, send an alert with description exactly: test
   Within ~2 seconds the widget count must increase and sound/light must fire.

3. Handle/update that alert in the CMS.
   The count must decrease and the sound must NOT replay.

4. Create a pending alert from the CMS.
   The widget count must NOT increase.

5. KEY TEST for this revision – the masked arrival:
   While an operator is handling alerts in the CMS, send a new alert from the
   app at the same moment. The widget must fire sound/light even if the
   displayed number does not change.

6. Do NOT expect the widget number to equal the CMS "Alertes pendents" total.
   A lower widget number is correct under the agreed rule.

7. If the widget was rebuilt: set the sound to 1' or 3', quit the widget
   completely, reopen it, and confirm the selection was retained.

8. Leave idle 2–4 hours and confirm no recurring disconnects.

9. Cleanup: in Alertes pendents, delete ONLY alerts whose description
   contains "test".


IF ANYTHING STILL MISBEHAVES
----------------------------
Please send both of these for the SAME time window:
  - widget log (macOS): ~/Library/Logs/FGC Widget APP/main.log
  - the server WebSocket log

Two notes on the server log that will speed up diagnosis:
  - Please include the hours immediately around the incident. The export sent
    on 3 August covered 31 July 00:00–08:20 only, which did not include the
    reported event.
  - The log currently mixes UTC and local (+02:00) timestamps on different
    lines, which makes simultaneous events look two hours apart. Aligning the
    timezone across the PHP-FPM and WebSocket processes would help.

In the new build, a masked arrival is visible in the server log as
"masked_arrival": true, alongside "max_alert_id".
