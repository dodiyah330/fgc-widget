FGC Widget – Confirmed server findings and deployment notes
============================================================
Date: 2026-07-25
Endpoint: ws://incivisme.fgc.cat:8080
Server: ReactPHP SocketServer + Ratchet v0.4.4 (direct, no proxy/LB)

CONFIRMED ROOT CAUSES
---------------------
1. WebSocket count did not match the CMS definition.
   The total shown in "Alertes pendents" comes from
   AlertRepository::getTotalAlerts(): state = pending AND user != 'prova'.
   WebSocketServer.php did not exclude 'prova' and additionally excluded
   updatedAt IS NOT NULL and fromCms IS NOT NULL records. Therefore, an edited
   pending alert or one created from the CMS could appear in "Alertes pendents"
   but be absent from the widget count, while pending 'prova' alerts were
   counted by the widget and not by the CMS.

2. Initial/reconnect count could be stale or missing.
   onOpen returned cached lastCount only. Before the first 14-second timer it
   sent nothing; afterward the value could be up to 14 seconds old.

3. Every application message was broadcast to every widget.
   ping, pong, sync, unknown message types, and stop_alerts were all global.
   Legacy clients interpret any typed message other than stop_alerts as a
   notification, so JSON heartbeat/sync traffic can create false alerts.

4. Timer/database exceptions were not contained.
   An exception escaping the ReactPHP periodic callback can terminate the
   long-running WebSocket process and disconnect all clients.

5. Any count change replayed notification behavior while count > 0.
   A decrease from 5 to 4 still used notify=true, causing unnecessary
   sound/blinking.

6. Normal delivery was delayed by design.
   The server queried for new incidents only every 14 seconds, so even a stable
   connection could not receive a new count immediately.

7. The shared broadcast baseline could be consumed by a connecting widget.
   Broadcasts are only emitted when the polled count differs from lastCount. Any
   path that refreshes lastCount outside broadcastAlerts() makes the next poll
   see "no change", so a widget connecting or syncing between two polls silences
   the new incident for every widget already connected.

WHAT THE PATCH CHANGES
----------------------
- Count query now mirrors the CMS total: state = 1 AND user != 'prova'.
- Every connection receives a fresh authoritative count immediately.
- onOpen/sync never modify lastCount, so they cannot suppress a broadcast.
- sync returns a fresh count only to its requester.
- application ping returns pong only to its requester.
- only stop_alerts is broadcast globally.
- notify=true only when the pending count increases.
- polling interval reduced from 14 seconds to 2 seconds.
- timer/query failures are logged and contained; the next cycle retries.
- failed client sends are isolated and the bad connection is closed.

KEEPALIVE CONCLUSION
--------------------
The client was correct that protocol keepalive already exists:

  $wsServer->enableKeepAlive($loop, 30)

Ratchet sends WebSocket control-frame pings. Chromium/Electron answers pong
control frames automatically. No JSON/application heartbeat is needed. The
widget's temporary JSON ping was removed because the old server rebroadcast
it globally.

DEPLOYMENT
----------
1. Replace:
   - src/WebSocketServer.php
   - src/Command/WebSocketServerCommand.php (unchanged behavior; included)
2. Restart the app:websocket-server process.
3. Deploy the rebuilt widget.
4. Confirm widget count equals the unfiltered CMS "Alertes pendents" total.
   Note: the polling interval constant POLL_INTERVAL_SECONDS is now 2. This runs
   one indexed COUNT query every 2 seconds; raise it if DB load is a concern.
5. Monitor server logs for "Error consultando alertas" and client logs for
   "[WS] connection closed" (code/reason/durationMs).

Patch files are under server-patch/ in the Widget repository.
