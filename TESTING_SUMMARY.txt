FGC Widget – Final testing summary
==================================
Date: 2026-07-25
Production endpoint: ws://incivisme.fgc.cat:8080

PRODUCTION CONNECTION TEST
--------------------------
Passive probe (no JSON ping/sync; protocol keepalive only):

  Run 1 duration:      4 minutes
  Connections opened:  1
  Spontaneous closes:  0
  Continuous session:  239,149 ms

  Run 2 duration:      20 minutes
  Connections opened:  1
  Spontaneous closes:  0
  Continuous session:  1,199,782 ms
  Final close:          code 1000, intentional probe_done
  Initial message:      {"alerts":0,"notify":false}

Result: 24 minutes of production connection time across two runs with a single
uninterrupted session each and zero spontaneous closes. Ten consecutive
2-minute windows passed without a disconnect, so the reported "disconnects
every two minutes" is NOT reproducible at the transport level from our network,
and Ratchet's 30-second protocol keepalive works with a standard client.

Consequence: the reported symptoms are explained by the application-level
defects listed below (stale/incorrect count, globally broadcast message types,
missed increments, 14-second polling) rather than by a periodic transport
timeout. An on-site soak on a previously affected FGC workstation is still
required to rule out a network-specific factor we cannot observe remotely.

SERVER PATCH TESTS
------------------
Command:
  php tests/server-websocket-smoke.php

Passed scenarios:
  - two-second pending-alert polling interval
  - fresh authoritative count on every connection
  - count query mirrors the CMS total (state=1 AND user != 'prova')
  - ping/pong remains private
  - sync response remains private
  - stop_alerts broadcasts to all clients
  - first cycle after restart publishes the count without replaying an alarm
  - unchanged count is not rebroadcast
  - count increase sends notify=true to every connected widget
  - count decrease sends notify=false
  - a widget connecting between polls does NOT suppress the pending
    notification for widgets already connected (regression test)
  - a sync request between polls does NOT suppress the next broadcast
  - database failure is contained inside the timer callback
  - broadcasting continues correctly after a client disconnects

  src/Command/WebSocketServerCommand.php     PASS

were not produced or tested in this engagement.

CONFIRMED BEFORE/AFTER
----------------------
Before:
  - WebSocket count excluded updated and CMS-created pending alerts, and
    included pending 'prova' alerts the CMS total excludes.
  - onOpen could return stale count or no count.
  - arbitrary message types were broadcast to every widget.
  - normal alert delivery could wait up to 14 seconds.
  - timer/database exception could escape the ReactPHP event loop.
  - reconnect was a fixed 5-second UI timer.
  - no sleep/wake recovery or useful close diagnostics.
  - fast initial snapshot could race the layout watcher.

After:
  - Server count mirrors the CMS Alertes pendents total exactly.
  - Connect/sync no longer consume the shared broadcast baseline.
  - Fresh count sent immediately on connect/reconnect.
  - Message types are explicitly routed; only stop_alerts is global.
  - Polling interval reduced to 2 seconds.
  - Timer/query errors are logged and contained.
  - Exponential reconnect (2–30 seconds), connection timeout, sleep/wake and
    online recovery.
  - Close code/reason/session duration written to electron-log.
  - Visible count derives directly from Pinia state (no initial race).
  - Higher reconnect snapshot triggers notification for alerts missed in gap.
  - Ratchet protocol heartbeat remains the sole heartbeat; no JSON ping storm.
